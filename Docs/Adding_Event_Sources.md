# Як додавати й імпортувати джерела

Кожен запис має окремий JSON у
`E:/PETprojects/Rodovid/Data/assets/documents/source-records/`.
Посилання й опис редагуються тільки в ньому. Скан необов’язковий;
за наявності він лежить поруч з однаковою основою назви:

```text
заприса-наталія-народження-PFFS-2YZ-6X32-NT61.json
заприса-наталія-народження-PFFS-2YZ-6X32-NT61.png
карпінська-анастасія-народження-PN7G-3MV-33S7-9R9B-QZW.json
```

Порядок частин: **прізвище-ім’я-типподії-IDлюдини-IDзапису**.
Для народження дитини використовуємо ім’я та ID дитини, для шлюбу —
одного з учасників. Зіставлення з людиною виконується за ID. Без FamilySearch
можна використати канонічний ID людини й місцевий номер, наприклад `акт-17`.

Підтримуються ID індексованих записів FamilySearch (`6X32-NT61`) і кадрів
(`33S7-9R9B-QZW`, `3Q9M-CS9T-LFDJ`). ID кадру не означає, що всі акти на ньому
є одним записом. Окремі джерела не зливаються за однаковим URL. Якщо двом
джерелам відповідає та сама основа назви, додається сталий суфікс ID джерела.

Типи в назвах: `народження`, `шлюб`, `смерть`, `хрещення`, `поховання`,
`проживання`, `інша-подія`. Якщо точної події немає, джерело може залишатися
прив’язаним до людини або родинного зв’язку; імпорт не створює факти з опису.

## Уточнення власника без нового документа

У `Data/annotations.json` точну дату додаємо через `additionalClaims`
із поясненням походження та обираємо через `primaryClaimIds`. Суперечливу
дату з наданого тексту зазначаємо в поясненні. Повідомлення власника
не створює метричний акт або нове джерело зі скриншотом.
Для службових приміток задаємо `publishReason: false`: `reason` залишається
в робочих даних і не потрапляє до пояснення твердження на сайті.

Явно повідомлений статус життя зберігаємо через `personEnrichments`:
`id`, `personId`, `lifeStatus` (`alive`, `deceased`, `unknown`) і `explanation`.
Прив’язка має посилатися на наявну людину; повторні уточнення однієї людини
та статус `alive` за наявності її події смерті відхиляються. Відсутність
дати смерті сама по собі не означає статус «Живий».

18.10.2026: для Николая Зубенка PFVG-PWS (I27) власник надав дату
народження 2 жовтня 1952 року, наявне місце Чапліївка та статус «Живий».
Згадку «лютий 1952 р.» із того самого повідомлення збережено в поясненні
до основної дати. Первинного акта немає.

## Вміст JSON

Рівно два поля, UTF-8:

```json
{
  "url": "https://www.familysearch.org/ark:/61903/1:1:6X32-NT61",
  "description": "Текст метричного запису.\nНаступний рядок."
}
```

`url` показується посиланням під скриншотом без підпису, `description` — як «Опис».
Коли посилання немає, вкажіть `"url": null`; коли опису немає —
`"description": ""`. Непевне читання позначайте `[нерозбірливо]`, власний
переказ відрізняйте від дослівної розшифровки. Імпортований опис сам по собі
не означає, що скан перевірений або факт підтверджений.

Один файл можна прив’язати до кількох людей, подій і тверджень без копіювання
опису та скану. `Data/annotations.json` містить прив’язки, медіа та пояснення
доказів; окремих редагованих копій основного опису й посилання там немає.
Первинні тексти та бібліографія залишаються у вихідному GEDCOM.

## Додавання JSON і скану

Підготуйте JSON у зручній папці архіву. PNG/JPG/JPEG/PDF можна покласти поруч
відразу або додати пізніше. З однаковою основою назви допускається один скан.

```powershell
cd E:\PETprojects\Rodovid
npm run source:add -- --input "E:/RodovidZubenko/SelectedBooks/папка/заприса-наталія-народження-PFFS-2YZ-6X32-NT61.json"
```

Без `--apply` команда лише перевіряє результат. Для збереження:

```powershell
npm run source:add -- --input "E:/RodovidZubenko/SelectedBooks/папка/заприса-наталія-народження-PFFS-2YZ-6X32-NT61.json" --apply
```

Команда знайде людину, подію та джерело, скопіює матеріали й збереже прив’язку.
Якщо вибір неоднозначний, використайте локальний майстер:

```powershell
npm run source:add
npm run source:list -- "Наталия"
```

Майстер дозволяє залишити URL і шлях до скану порожніми, вибрати точну подію
та наявне джерело. Вже прив’язане джерело зберігає назву файла й свої ID.

Після першого додавання редагуйте JSON у `Data/assets/documents/source-records/`.
Для додавання картинки до наявного запису покладіть її поруч з однойменним
JSON. Наступна підготовка даних зареєструє скан. Можна також повторити
`source:add --input ... --apply`. Довільно перейменовувати вже прив’язані
файли не слід: потрібно також оновити службові прив’язки.

## Опис із GEDCOM

Після погодженого імпорту GEDCOM та зіставлення стабільних ID підготовка
`npm run data:convert`, dev-сервер і збірка автоматично синхронізують джерела:

- новому джерелу створюється JSON, навіть без скану;
- незмінені вручну поля оновлюються з нового імпорту;
- змінені вручну поля зберігаються; якщо імпорт теж змінив їх — формується
  розбіжність із попереднім, поточним та новим варіантами;
- порожнє поле чи відсутнє в наступному експорті джерело не видаляє локальні
  матеріали, опис і прив’язки;
- опис і URL порівнюються окремо, тому конфлікт опису не блокує оновлення URL.

Окремий запуск із попереднім переглядом:

```powershell
npm run source:sync
npm run source:sync -- --apply
```

`source:sync` без `--apply` не змінює дані, лише записує звіт у `tmp/`.
`npm run data:validate` також перевіряє запланований результат без застосування.
Повторний запуск без змін не перезаписує JSON і не створює резервних копій.

## Як розв’язати розбіжність

Збірка зберігає локальний варіант і повідомляє про розбіжності.
Порівняння є у `tmp/data-conversion.json.md`; після окремого `source:sync` —
у `tmp/source-record-sync-report.json.md` і відповідному JSON-звіті.
До явного рішення розбіжність залишається у наступних звітах.

Залишити ручні правки та прийняти новий імпорт як базу наступних порівнянь:

```powershell
npm run source:sync -- --resolve source-ID --keep-local --apply
```

Використати новий імпортований варіант:

```powershell
npm run source:sync -- --resolve source-ID --use-import --apply
```

Замість `source-ID` вкажіть ID із звіту; звіт також містить готові команди.
Можна вручну скласти потрібний текст у JSON і потім виконати `--keep-local`.
Вибір стосується полів зазначеного джерела. Перед записом перевіряються дані;
одночасна зміна файлів зупиняє застосування.

`Data/source-record-imports.json` — службовий знімок попередніх імпортів,
вихідних джерел і прив’язок для порівняння та збереження пропущених джерел.
Його не потрібно редагувати вручну. Це не альтернативний файл редагування
опису; сайт бере поточний текст із JSON у `source-records`.

## Резервні копії та сайт

### Черга додавання скриншотів

Погоджений порядок від 2026-10-18: спочатку джерела прямих предків домашньої
особи `I1` по обох батьківських лініях, від ближчих поколінь до давніших.
Побічні гілки опрацьовуємо після них. Прямих предків визначаємо переходами
від дитини до батьків у поточних даних; шлюб сам по собі не робить людину предком.

Уточнений порядок: працюємо групами схожих джерел однієї події.
Надаємо разом посилання дитини/подружжя та батьків і наявний опис;
власник перевіряє, чи вони стосуються того самого акта. Прив’язка до
однієї події та схожі ID є підставою запропонувати групу, але самі по
собі не підтверджують однаковість записів. Після підтвердження власника
поширюємо погоджені скриншот і опис на відповідні джерела групи.
Якщо збереженого скриншота немає, отримуємо його від власника.
Якщо опису немає, спочатку готуємо текст за зображенням і чекаємо погодження;
після погодження зберігаємо опис і скриншот разом. Після кожного збереження
повідомляємо залишок джерел без зображень серед прямих предків і в усьому наборі.
Нове уточнення власника: текст готуємо мовою документа як транскрипцію,
зберігаючи оригінальне написання імен і дореформені літери. Не замінюємо
імена сучасними українськими відповідниками. Нечитабельні й закриті згином
місця без відомого читання позначаємо явно у квадратних дужках. Відомі
частини, закриті згином (наприклад, «Александровъ»), за уточненням власника
відновлюємо з контексту без позначки у погодженому описі. Підставу такого
відновлення зберігаємо в журналі доповнення. Переклад додаємо лише на окреме прохання.
Для Павла Дейкала (25.01.1924, `6X3L-D392` / `6X3L-D39P`) власник
підтвердив відновлення «Александровъ» та остаточний текст із
«Ксенія Николаева»; цей погоджений варіант збережено для обох джерел.

### Один акт і кілька людей

Уточнення власника від 2026-10-18: одна подія та її джерело можуть бути
прив’язані до кількох людей у різних ролях. Народження стосується дитини
і її батьків; шлюб — подружжя та їхніх батьків, зазначених у записі.
Такі прив’язки нормальні й самі по собі не є помилковими дублями.

Зберігаємо спільну подію та окремі прив’язки доказів до відповідних людей
і тверджень. Окремі індексовані записи FamilySearch для учасників одного
акта можуть мати різні ID та посилання; не видаляємо й не зливаємо їх лише
через спільний скриншот. Не створюємо повторну подію для кожного учасника.
Ролі й зв’язки визначаємо за записом або явним уточненням власника.

18.10.2026 власник відхилив `source-yakov-families-2026-10-17`:
скриншот дерева FamilySearch не є валідним джерелом. Джерело, усі вісім
прив’язок, JSON і скриншот видалені з даних сайту в усіх людей.
Самі люди, події та родинні зв’язки збережені. Зворотна копія вилучених
матеріалів: `tmp/rejected-tree-source-1792337191112/`.

У секції джерела однієї події однакові за вмістом скани показуємо разом:
картинка й ідентичний опис відображаються один раз, усі зовнішні посилання
та прив’язки цитувань зберігаються. Підготовка обчислює SHA-256 файлів;
різні скани й різні варіанти опису залишаються видимими окремо.
Посилання розміщуємо під скриншотом, без підпису «Зовнішнє посилання».
Кілька посилань ідуть в один рядок із переносом за потреби на вузькому
екрані. Якщо скриншота ще немає, посилання залишаються після опису.

У подіях життя шлюб показуємо лише самому подружжю. Згадка батьків
у шлюбному акті дітей дає прив’язку доказу до батьків, але не додає
шлюб дітей до життєпису чи попапа батьків. Народження дітей і далі
може відображатися в подіях життя їхніх батьків.

Синхронізація зберігає попередні файли й перелік створених у
`tmp/source-record-sync/<запуск>/`; локальний майстер — у `tmp/source-records/`.
Точний шлях друкується в результаті. Для відновлення скопіюйте збережені
файли назад; `changes.json` показує, які файли створено вперше.

Відсутній зареєстрований JSON, пошкоджений JSON або відсутній уже прив’язаний
скан зупиняє підготовку. Відсутність скану в запису, який ще не мав картинки,
помилкою не є. Неприв’язані матеріали довільно з архіву не публікуються.

Dev-сервер оновлює сайт після змін. Для опублікованого сайту потрібні збірка
й публікація. Редактора та завантаження через сайт немає. Службові JSON,
вихідний GEDCOM і резервні копії до публічної збірки не входять.
