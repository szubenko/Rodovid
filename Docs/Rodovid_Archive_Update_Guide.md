або виключена з індексу. `.git` у процедурі нижче не копіюється; це знімок
файлів із кодом, а не резервування всієї історії Git.

## 2. Резервна копія перед змінами

Збережіть документи й закрийте RootsMagic, редактори матеріалів та локальний
сервер. Копіюйте `.rmtree` лише після закриття RootsMagic; для відкритої бази
потрібен узгоджений SQLite backup, а не копія одного файла. Не змінюйте
джерело під час копіювання. Переконайтеся, що вистачає місця.

У PowerShell визначте дві функції. Вони копіюють у **нову папку**, зберігають
приховані файли, перевіряють перелік, розміри й SHA-256; посилання на інші
каталоги потребують окремого включення реальних файлів.

```powershell
$ErrorActionPreference = 'Stop'
function Get-ArchiveManifest([string]$Root) {
    $base = (Resolve-Path -LiteralPath $Root).Path.TrimEnd('\')
    Get-ChildItem -LiteralPath $base -Force -Recurse | ForEach-Object {
        if ($_.Attributes -band [IO.FileAttributes]::ReparsePoint) {
            throw "Посилання потрібно резервувати окремо: $($_.FullName)"
        }
        if (-not $_.PSIsContainer) {
            [pscustomobject]@{
                Path = $_.FullName.Substring($base.Length + 1)
                Bytes = $_.Length
                SHA256 = (Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256).Hash
            }
        }
    } | Sort-Object Path
}
function New-ArchiveSnapshot([string]$Source, [string]$Destination) {
    $sourcePath = (Resolve-Path -LiteralPath $Source).Path.TrimEnd('\')
    $destinationPath = [IO.Path]::GetFullPath($Destination).TrimEnd('\')
    if ($destinationPath.Equals($sourcePath, [StringComparison]::OrdinalIgnoreCase) -or
        $destinationPath.StartsWith($sourcePath + '\', [StringComparison]::OrdinalIgnoreCase)) {
        throw 'Копія має лежати поза джерелом'
    }
    if (Test-Path -LiteralPath $destinationPath) { throw 'Оберіть нову папку копії' }
    # Виключаються лише ці папки в корені; весь Data копіюється без винятків.
    $skip = @('.git', 'node_modules', 'dist', 'generated', 'tmp', 'temp',
        '.cache', '.npm-cache', '.vite', '.vitest', 'coverage',
        'playwright-report', 'test-results', 'blob-report')
    $items = @(Get-ChildItem -LiteralPath $sourcePath -Force |
        Where-Object { $_.Name -notin $skip })
    $before = @(foreach ($item in $items) {
        if ($item.Attributes -band [IO.FileAttributes]::ReparsePoint) { throw "Посилання: $($item.FullName)" }
        if ($item.PSIsContainer) {
            Get-ArchiveManifest $item.FullName | ForEach-Object {
                $_.Path = $item.Name + '\' + $_.Path
                $_
            }
        } else {
            [pscustomobject]@{ Path = $item.Name; Bytes = $item.Length
                SHA256 = (Get-FileHash -LiteralPath $item.FullName -Algorithm SHA256).Hash }
        }
    })
    if ($before.Count -eq 0) { throw 'Порожнє джерело' }
    $payload = Join-Path $destinationPath 'files'
    New-Item -ItemType Directory -Path $payload | Out-Null
    foreach ($item in $items) {
        Copy-Item -LiteralPath $item.FullName -Destination $payload -Recurse -Force
    }
    $after = @(Get-ArchiveManifest $payload)
    if (Compare-Object $before $after -Property Path, Bytes, SHA256) {
        throw 'Копія не збігається: не використовуйте її для відновлення'
    }
    $before | Sort-Object Path | Export-Csv -LiteralPath (Join-Path $destinationPath 'manifest.csv') -NoTypeInformation -Encoding UTF8
    Write-Output "Перевірено $($after.Count) файлів: $destinationPath"
}
```

Оберіть свою папку резервування поза проєктом і сімейним архівом. Нижче —
приклад; якщо диска `E:` немає, змініть шляхи. Виконуйте в тій самій сесії:

```powershell
$snapshotRoot = 'E:\RodovidBackups\' + (Get-Date -Format 'yyyyMMdd-HHmmss')
New-ArchiveSnapshot 'E:\PETprojects\Rodovid' (Join-Path $snapshotRoot 'site')
New-ArchiveSnapshot 'E:\RodovidZubenko' (Join-Path $snapshotRoot 'originals')
```

Для сімейного архіву `tmp/` вважається тимчасовим: перенесіть єдині потрібні
оригінали з нього до постійного сховища **до** резервування. У копії `originals`
мають бути `Magic/`, `Books/`, `SelectedBooks/` і нотатки, які існують у джерелі.
Перевірте кілька файлів відкриттям. Зберігайте попередні перевірені знімки;
після успішного оновлення зробіть ще один. Другу копію з маніфестами збережіть

## 4. Повторний експорт та стабільні ID

SHA-256 обчислюється з **точних байтів**, включно із закінченнями рядків:

```powershell
(Get-FileHash -LiteralPath 'Data/Zubenko.ged' -Algorithm SHA256).Hash.ToLowerInvariant()
```

Якщо SHA вже є в `Data/identities.json.imports`, повторно його не додавайте.
Для іншого SHA потрібен один новий `{ "id": "import-2026-09-28", "sha256": "…" }`
і нове походження у відповідних `entries[].origins`. Старі походження та
`entity.id` зберігаються. **Не запускайте `--init-identities` для повторного
експорту** й не замінюйте весь журнал новоствореним.

Реальний приклад поточного імпорту: новий `@I4@` зберігає канонічний `I3`
та адресу `/person/I3`; новий `@I3@` належить іншій людині з ID `I26`.
Дивіться [розгляд імпорту 17.09.2026](Rodovid_Import_2026-09-17.md).
Форма запису нижче ілюстративна; значення `importId` мають існувати в `imports`:

```json
{
  "entity": { "kind": "person", "id": "I3" },
  "origins": [
    { "importId": "old-import", "recordId": "@I3@" },
    { "importId": "new-import", "recordId": "@I4@" }
  ]
}
```

Зіставляйте не лише людей: сім’ї, зв’язки, події, твердження, місця,
джерела й цитування також мають власні ID. Шлях `BIRT[0].DATE[0]` означає
першу дату першого народження; індекси починаються з нуля. Перестановка
двох `BIRT` потребує зіставлення їхніх вкладених шляхів. Зв’язок може мати
шлях `HUSB[0]+CHIL[0]`; цитування — додатковий суфікс цілі.
Не копіюйте походження масово, доки не перевірено відповідність кожного запису.

Новій сутності надайте невикористаний ID; вилученій не додавайте походження
нового імпорту, але залиште попередню історію. Не перевикористовуйте її ID.
Ім’я або той самий XREF не доводять тотожності. Незмінний FamilySearch ID
може допомогти зіставленню, але потребує перевірки й не є історичним доказом.
За неоднозначності залиште оновлення неприйнятим і розберіть запис вручну.

У журнал оновлення запишіть відповідності, нові/неактивні ID та причини
вилучення чи зміни фактів. Неприв’язане доповнення не видаляйте, щоб
«пройшов build»: виправте відповідність, або після предметного рішення
перенесіть його до окремого архіву разом із поясненням та старим набором.
Формати: [конвертація](Rodovid_Data_Conversion_v1.md),
[контракт](Rodovid_Data_Contract_v1.md), [схема журналу](../src/data/identity.ts).

## 5. Заміна й прив’язка матеріалів

`media[].path = "assets/documents/record.pdf"` означає
`Data/assets/documents/record.pdf`; `--assets-root`, якщо потрібен, вказує
на `Data`, а не `Data/assets`. Використовуйте `/` у JSON-шляхах.
Не посилайтеся на `Downloads`, тимчасові папки, `..` або абсолютні шляхи.

- Для нової підготовленої версії того самого документа збережіть його
  `media.id` і прив’язки, замініть байти файла. За іншого імені/формату
  оновіть `path`, `mimeType`, мініатюру та її MIME. Розміри JPG/PNG
  конвертер визначає сам. Новому самостійному матеріалу потрібен новий ID.
- Перевірте, що обрізання або перестановка сторінок не змінили зміст
  `evidenceLinks[].fragment`: номер сторінки PDF й область зображення
  мають указувати на той самий доказ. Збережіть реквізити, транскрипцію,
  походження та оцінку **конкретного** твердження/зв’язку.
- Джерело оголошує `mediaIds`, доказ — `sourceId` і `target`; одне джерело
  можна прив’язати до кількох фактів без дублювання файла.
  Аудіо вибирають за ID у `site.json.audio`.
- Спогади: змінюйте Markdown-файл із `memoryFiles[].markdownFile`; зберігайте
  `id`, `personIds`, заголовок і походження. Або редагуйте `memories[].markdown`
  для тексту, який зберігається прямо в доповненнях. Не створюйте обидва
  записи з одним ID. Довільний HTML не є способом оформлення спогадів.
- Повний оригінал тримайте окремо, у сімейному архіві чи `Data/originals/`.
  Оголошення файла у `media` включає його до збірки навіть без прив’язки
  до кімнати. Не оголошуйте архівні оригінали або тестові приклади.

Конкретні поля перевіряйте за [схемою доповнень](../src/data/supplements.ts)
та [правилами матеріалів](Rodovid_Static_Build_v1.md). Збірка не оптимізує
зображення; читабельність дрібного тексту та якість звуку перевіряйте вручну.

Фотографії оголошуйте в `media`, а до людини прив’язуйте через
`personMedia` у `Data/annotations.json`:

```json
{
  "id": "person-media-i103",
  "personId": "I103",
  "photoIds": ["media-i103-history-photo"],
  "portraitId": "media-i103-diagram-portrait"
}
```

`photoIds` задає тільки знімки секції «Фотографії», а `portraitId` —
портрет для карток діаграм і спливних відомостей. Це незалежні прив’язки:
портрет не додається в галерею автоматично. Для `I103` круглий портрет
призначено тільки для діаграм і підказки, у галереї — фото у кріслі.
Конвертер перевіряє людину, медіа-ID та відсутність повторних призначень.
Портрет також зберігається в PNG-експорті.

Для підготовленої біографії використовуйте `memories` або `memoryFiles`
із `personIds` та Markdown. Текст і фотографії з `mediaIds` показуються
в наявній секції «Спогади» вкладки «Історія життя»; окремої секції
«Біографія» немає (уточнення власника 30.10.2026).
Для Ярослава Чабана `I103` повний наданий текст збережено
в `memories[].markdown`, фото у кріслі — у `mediaIds` цієї біографії.
Редагуйте робочий текст у доповненнях, оригінал зберігайте в сімейному архіві.

## 6. Перевірка, помилки, build і перегляд

Виконуйте з кореня **робочої копії**. Кожен ненульовий код означає зупинку:

```powershell
npm run data:validate
if ($LASTEXITCODE -ne 0) { throw 'Читайте звіт; build поки не запускати' }
Get-Content -Raw 'tmp/data-conversion.json.md'
npm run data:convert
if ($LASTEXITCODE -ne 0) { throw 'Конвертація неуспішна' }
```

Прочитайте також JSON-звіт: `validation.status`, `validation.totals`,
`validation.issues`, `unhandledNodes`, `reviewNotes`, `sha256` і `counts`.
`warning` не означає історичне підтвердження; кожне нове попередження
потрібно розглянути. `info` пояснює, наприклад, допустимий порожній розділ.

| Повідомлення | Де виправляти |
| --- | --- |
| `PREPARATION_FAILED`, помилка JSON/Zod | Читайте вкладений текст і шлях поля; перевірте синтаксис та поля `site.json`, `annotations.json`, `identities.json` або названий Markdown. |
| `Expected one import for SHA-256`, `Missing explicit identity mapping`, `Unused identity mapping` | `identities.json`: точний SHA, `importId`, тип, XREF та шлях у поточному GEDCOM. Не ініціалізуйте журнал заново. |
| `Unresolved…`, `INVALID_REFERENCE_OR_ID`, неприв’язане доповнення | За ID знайдіть запис у доповненнях/налаштуваннях і його канонічну ціль. Перевірте зіставлення або предметно розберіть вилучення. |
| `INVALID_DECLARED_FILE` | Названий файл і запис `media`: існування, шлях, MIME, сигнатура, мініатюра. Перейменування розширення не конвертує файл. |
| `INVALID_MEDIA_ROLE` | Прив’язка фото, портрета, аудіо чи фрагмента доказу до відповідного типу файла. Портрет і галерея мають незалежні списки ID. |
| `UNSUPPORTED_STRUCTURE` | XREF/рядок/шлях GEDCOM, деталі в `unhandledNodes`. Збережіть відомості; потрібне доповнення конвертера або обґрунтоване перенесення в підтриману структуру, не видалення тега навмання. |
| `ANCESTRY_CYCLE`, `CONFLICTING_ROLES`, `POSSIBLE_DUPLICATE_FAMILY` | Вихідні сімейні записи за XREF та зв’язки за ID; ручний розгляд. Не змінюйте факт лише для обходу валідації. |
| `INVALID_CALENDAR_DATE`, `REVERSED_DATE_RANGE` | Дата конкретної події/твердження у GEDCOM або доповненні. Зберігайте оригінал і невизначеність, не підставляйте вигаданий день. |

цієї інструкції стосувалися попереднього експорту. Після виправлення
обліку `SEX` 29.10.2026 поточний набір має 0 помилок і 12 попереджень
`EMPTY_EVENT_CONTEXT` про порожні `MARR`; вони не створюють подій шлюбу.
Підтримані значення `SEX` перенесені в `Person.sex`, а непідтримані
структури залишаються помилками. Точний перелік звіряйте зі свіжим звітом.
Історичний дозвіл невирішених D07/D08
прив’язаний до SHA і точних зв’язків у
[`reviewed-export.ts`](../scripts/validation/reviewed-export.ts).
Навіть текстова зміна GEDCOM потребує нового розгляду; не підміняйте там
контрольну суму автоматично. `data:check-gedcom` перевіряє **історичний**
знімок 02.09.2026, а не новий вхід.

Порівняйте початковий і новий `family.json` за канонічними ID, а не лише
кількостями: усіх людей, кінці зв’язків, події/дати/місця, усі альтернативні
твердження та основний варіант, оцінки, джерела/докази/фрагменти, спогади,
медіа й кімнати. Для кожної втрати чи заміни потрібна пояснена зміна.
Валідація не може знати, чи навмисно вилучено цілий коректний запис!
Для зміни лише матеріалу решта предметних даних має лишитися тотожною.
Після правок зіставлення або конвертера додатково виконайте `npm test`
та `npm run lint` з перевіркою коду завершення.

```powershell
npm run build
if ($LASTEXITCODE -ne 0) { throw 'Немає нової прийнятої збірки' }
npm run preview -- --port 4175
```

Відкрийте `http://127.0.0.1:4175/tree/I1`, змінені `/person/<ID>` і
прямі адреси файлів. Звірте версію `data/family.json`, домашню особу,
пошук, зв’язки, змінені матеріали та збільшення документів. Оновіть сторінку;
вже відкрита вкладка може тримати попередній JSON. `Ctrl+C` зупиняє сервер.
`preview` сам не перебудовує файли; для `dev` після зміни `Data/` потрібен
перезапуск. Зайнятий порт змініть, не завершуйте чужі процеси.

Після помилки попередні `generated/family.json` та `dist/` можуть лишитися
на диску. Їх наявність **не означає успіх нового оновлення**. Якщо звіт
не записався, дивіться stderr і перевірте права/шляхи. Збережіть свіжий звіт
та результат огляду у журналі; приймайте нову копію лише після успіху.
Ця процедура локальна. Захищена публікація — окремі ROD-029…034.

## 7. Відновлення без змішування версій

Зупиніть сервер і збережіть невдале оновлення окремим знімком для аналізу.
Відновлюйте **в нову порожню папку**, не поверх частково зміненого `Data/`:
інакше можуть залишитися зайві файли або несумісні версії журналу й GEDCOM.
Визначені в розділі 2 функції мають бути доступні в цій PowerShell-сесії.

```powershell
$savedSnapshot = 'E:\RodovidBackups\20260928-120000\site' # оберіть наявну копію
$restoredProject = 'E:\PETprojects\Rodovid-restored-20260928' # нова папка
$payload = Join-Path $savedSnapshot 'files'
$expected = @(Import-Csv -LiteralPath (Join-Path $savedSnapshot 'manifest.csv'))
if ($expected.Count -eq 0) { throw 'Маніфест порожній' }
$actual = @(Get-ArchiveManifest $payload)
if (Compare-Object $expected $actual -Property Path, Bytes, SHA256) { throw 'Копія пошкоджена або неповна' }
if (Test-Path -LiteralPath $restoredProject) { throw 'Потрібна нова папка відновлення' }
New-Item -ItemType Directory -Path $restoredProject | Out-Null
Get-ChildItem -LiteralPath $payload -Force | ForEach-Object {
    Copy-Item -LiteralPath $_.FullName -Destination $restoredProject -Recurse -Force
}
$restored = @(Get-ArchiveManifest $restoredProject)
if (Compare-Object $expected $restored -Property Path, Bytes, SHA256) { throw 'Відновлення неповне' }
Set-Location -LiteralPath $restoredProject
npm ci
if ($LASTEXITCODE -ne 0) { throw 'Не вдалося відновити залежності' }
npm run data:validate
if ($LASTEXITCODE -ne 0) { throw 'Відновлені дані не пройшли перевірку' }
npm run build
if ($LASTEXITCODE -ne 0) { throw 'Відновлена збірка неуспішна' }
npm run preview -- --port 4175
```

Звірте попередню версію JSON і байти матеріалів із журналом до оновлення,
відкрийте старий спогад/скан. Лише після цього використовуйте відновлену
папку як робочий проєкт. Архів `originals` відновлюється аналогічною
перевіркою маніфесту та копіюванням у нову папку, **без npm-команд**;
перевірте читання бази у RootsMagic і відкриття оригіналів.

## 8. Перевірка процедури

Перед першим реальним оновленням: зробіть знімок тестової копії, змініть
матеріал і його `dataVersion`, пройдіть розділи 5–6, потім відновіть у ще
одну папку за розділом 7. Перевірте повернення і даних, і файлів.
Окремо випробуйте відсутній файл та неприв’язане доповнення: підготовка
має зупинитися з поясненням. Тестові матеріали не переносіть до `Data/`
сімейного проєкту.

Фактичний прогін і межі перевірки: [протокол ROD-027](Rodovid_Archive_Update_Check_2026-09-28.md).
ROD-026 ще не завершено: реєстр, читабельність та приймання реальних
релізних матеріалів залишаються окремою роботою.
