# Контракт даних Rodovid v1

ROD-002, 2026-09-09. Виконуване визначення контракту — Zod-схеми у
[`src/data/`](../src/data/schema.ts); TypeScript-типи виводяться через `z.infer`,
а тип вхідного набору — через `z.input`. Встановлено Zod **4.5.4** із точним
lockfile; версію перевірено через офіційний npm. Використані `strictObject`,
дискриміновані об'єднання й значення за замовчуванням відповідають
[документації Zod](https://zod.dev/v4/changelog).

| --- | --- |
| `Data/Zubenko.ged` | Основні генеалогічні відомості; робочий експорт RootsMagic. |
| `Data/Zubenko.rmtree` | Робоча база; не входить у браузерний контракт. |

| [`Data/annotations.json`](../Data/annotations.json) | `supplementsSchema`: додаткові оцінки, основні варіанти, матеріали та відомості без погодженого представлення в GEDCOM. ROD-005 додав пояснення невизначеностей D01–D06; матеріали відсутні. |
| [`Data/identities.json`](../Data/identities.json) | `identityManifestSchema`: журнал стабільних ID та явних зіставлень між експортами. Створений ROD-005 за SHA-256 базового GEDCOM. |
| `assets/` | Підготовлені файли з ідентифікаторами `Media`; вихідні архівні шляхи не є URL сайту. |
| `generated/family.json` | Результат `npm run data:convert` за `familyDataSchema`, **не редагується вручну**, виключений з Git. Інтеграція зі збіркою — ROD-007. |

Поточний застосунок ще не завантажує родовід. ROD-002 визначає контракт і
приклади; ROD-003/005 реалізують парсер, злиття доповнень і [генерацію](Rodovid_Data_Conversion_v1.md). Реальний
GEDCOM і база не змінені. Синтетичні файли не імпортуються стартовим екраном
і не потрапляють у збірку.

`schemaVersion: 1` задає версію структури; `config.dataVersion` — версію
підготовленого вмісту. Несумісна зміна структури потребує нової версії й
явної міграції. `datasetKind` відрізняє `family` від `synthetic`.

Усі об'єкти строгі: невідоме поле спричиняє помилку замість тихої втрати.
Необов'язкове поле пропускається; `null` не означає невідоме значення.
Необов'язкові колекції після розбору стають `[]`. Рядки джерел не обрізаються
та не нормалізуються схемами.

## Сутності та зв'язки з §12.3 ТЗ

| Сутність / схема | Дані й посилання |
| --- | --- |
| `SiteConfig` / `siteConfigSchema` | `homePersonId → Person`, кімнати `personId → Person`, фон і звук `→ Media`. |
| `Person` / `personSchema` | Один `id`; імена через `Claim(field=name)`, події через `Event.participants`, родичі через `Relationship`, `photoIds` і `portraitId → Media`, зовнішні індекси, явний життєвий статус. |
| `Relationship` / `relationshipSchema` | `parent-child`: від батька/матері до дитини; `spouse`: ненапрямлена пара. Обидві кінцеві точки `→ Person`; оцінка, пояснення та статус ручного розгляду. Докази через `EvidenceLink`. |
| `Claim` / `claimSchema` | Ціль, поле, типізоване значення, `isPrimary`, оцінка й пояснення; джерела через `EvidenceLink(target.kind=claim)`. |
| `FamilyEvent` / `eventSchema` | Тип, необов'язкова назва, учасники `→ Person` з ролями, `relationshipIds → Relationship`, `mediaIds → Media`; дата, місце, опис і причина через твердження. |
| `Place` / `placeSchema` | Вихідна назва, окрема відображувана та історичні назви, адміністративна належність, необов'язкові координати й опис. |
| `Source` / `sourceSchema` | Документ/джерело: назва, опис, архів, шифр, HTTP(S)-посилання, дата внесення, `mediaIds → Media`. Може бути тільки бібліографічним записом без файла чи URL. |
| `Media` / `mediaSchema` | Повний підготовлений файл, його відносний шлях, MIME, назва й опис; необов’язковий `thumbnail: { path, mimeType }` (JPEG/PNG для фото чи PDF, ROD-007). Використовується документами, фото, подіями, спогадами та оформленням. |
| `EvidenceLink` / `evidenceLinkSchema` | `sourceId → Source`, ціль `Person / Event / Claim / Relationship`, конкретний фрагмент, транскрипція, власне пояснення та вихідний `QUAY`. |
| `Memory` / `memorySchema` | `personIds → Person`, заголовок і Markdown, необов'язкові автор, дата запису, `mediaIds → Media`. Не змінює оцінки фактів. |

Імена та фактичні значення зберігаються у твердженнях, щоб основне й
альтернативне значення не розходилися з окремою копією у картці чи події.
Картка знаходить ім'я за `(target.kind=person, target.id, field=name)`;
біографія знаходить дату за `(target.kind=event, target.id, field=date)`.
`Claim.value` має власну схему для кожного поля:

- `name` — лише для людини; сире й відображуване ім'я, необов'язкові складові та мова;
- `date` — лише для події; `HistoricalDate`;
- `place` — лише для події; ID місця;
- `description` — текст про людину або подію;
- `cause` — текст про подію (причина смерті належить події смерті).

Альтернативи одного факту мають однакові ціль і поле та різні ID. Основний
варіант позначається тільки за явним рішенням у GEDCOM або доповненнях.
У групі може бути **не більше одного** `isPrimary: true`. Якщо вибір не
заданий, усі варіанти залишаються доступними без вигаданого основного;
інтерфейс показує відсутність вибору. Порядок масиву не визначає основний факт.
Самостійні повторні події та сім'ї не зливаються лише через однаковий тип,
дату чи склад; конвертер зберігає їхнє походження та повідомляє повтори.

Родинний зв'язок має власну оцінку. `reviewStatus: accepted` означає прийняте
рішення про використання зв'язку, а не автоматичне «Підтверджено».
Невирішені шляхи (`unreviewed` / `disputed`) не дають безумовних точних
підписів спорідненості. Батьківство береться з явних вихідних зв'язків,
не виводиться зі шлюбу. Сирі `FAM` залишаються у проміжному результаті
парсера; їхні ID зберігаються в походженні зв'язків/подій та журналі ID.

## Дати та неповні відомості

[`historicalDateSchema`](../src/data/dates.ts) не використовує `Date` або
мітки часу. Рік не перетворюється на 1 січня.

| `kind` | Значення |
| --- | --- |
| `unknown` | Немає відомої дати; необов'язковий `raw` зберігає знак питання чи інший вихідний маркер. |
| `phrase` | Нерозібраний текст або непідтримана форма, зі збереженням `raw`, календаря та пояснення за наявності. |
| `point` | `value.precision`: `year`, `month` або `day` із відповідними компонентами; `qualifier`: `exact`, `about`, `estimated`, `calculated`, `before`, `after`. |
| `range` | Невизначена дата між `from` і `to`; кожна межа має свою точність. |
| `period` | Тривалість від `from` і/або до `to`; принаймні одна межа обов'язкова. |

Кожна відома форма має обов'язкові `raw` і `calendar`. Для неявного календаря
використовується `unspecified`; явний GEDCOM calendar escape зберігається
дослівно. Розбір та історичні календарні перерахунки не виконуються схемою.
Непідтриманий календар/подвійний рік зберігається як `phrase` до реалізації
підтримки; втрату точності треба відобразити у звіті парсера.

Схеми перевіряють форму компонентів та базові межі (місяць 1–12, день 1–31).
Кількість днів конкретного місяця, високосність у конкретному календарі,
порядок меж і суперечності хронології — предметна перевірка ROD-006/017.
Схема не видає структурно коректну дату за історично перевірений факт.

`Person.sex` — необов’язковий буквальний код GEDCOM M/F/U; конвертер переносить лише єдине відоме значення SEX, без виведення зі шлюбу чи імені. Походження — вихідний запис Person. Невідоме або суперечливе значення не домислюється.

`Person.lifeStatus` — `alive`, `deceased` або `unknown` (типово). Відсутність
смерті не доводить, що людина жива; запис про смерть без дати може явно
задавати `deceased`. Конвертер має зберегти підставу статусу в `provenance`.
Немає координат, фото, документа, спогаду чи дати — поле/колекція відсутнє
або порожнє відповідно до схеми; нульові координати не є заглушкою.

## Достовірність і докази

`confirmed` → «Підтверджено», `probable` → «Ймовірно», `hypothesis` →
«Гіпотеза», `unassessed` → «Не оцінено». Відсутня оцінка стає `unassessed`.
Оцінка належить конкретному твердженню чи зв'язку, а не всій людині.

`EvidenceLink.quay.raw` зберігає сирий текст, необов'язковий `value` —
розібране число 0–3. Це якість цитування джерела, яка **не перетворюється**
автоматично на `confidence`. Окремого погодженого правила такого перетворення
ще немає. FamilySearch ID у `Person.externalIds` та `SOUR RootsMagic` у
заголовку не створюють історичних доказів.

Один `Source` може мати будь-яку кількість `EvidenceLink`. Сам файл живе
в одному `Media`. Посилання можуть показувати різні фрагменти одного файла:
`page` — номер сторінки PDF від 1, `frame` — номер/назва кадру, `folio` —
оригінальне позначення аркуша, `recordNumber` — номер акту. `region` задає
частки ширини/висоти з початком у верхньому лівому куті зображення.
`fragment.mediaId` має належати до `Source.mediaIds`; транскрипція та
пояснення належать конкретній прив'язці.

Медіашляхи — переносні `assets/<папки>/<ім'я>.<розширення>` з ASCII-літер,
цифр, `_` та `-`; назва для читача зберігається окремо. Абсолютні Windows-шляхи,
`..` і зовнішні URL тут заборонені. Шлях — логічний шлях підготовленого
файла від кореня збірки; остаточне копіювання, перевірка MIME/розширення,
існування та розміру файла належать ROD-007. Markdown спогадів відображається
без виконання довільного HTML (ROD-019).

## Походження та стабільні ID

Кожна основна сутність має непорожній `provenance`:

- `gedcom`: `importId`, сирий `recordId` із `@`, необов'язковий точний `path` до вкладеного запису;
- `supplement`: відносний вихідний `file` та стабільний `entryId` доповнення.

Це технічне походження, а не оцінка історичної достовірності. Кілька
походжень не означають автоматичного злиття людей чи сімей.

Канонічні ID чутливі до регістру; допускають ASCII-літери, цифри, `.`, `_`,
`:` і `-`, починаються з літери/цифри. ID людини починається з `I` та має
принаймні один наступний символ. ID унікальний у своїй колекції; посилання
містить тип цілі там, де можливі різні колекції.

На **першому імпорті** `initialPersonId('@I1@')` дає `I1`. У налаштуваннях
`homePersonId: "I1"` посилається саме на початковий `@I1@`. Адресний сегмент
— `I1`, без `@`; `personIdToRoute` / `personIdFromRoute` перевіряють цей
формат. Наприклад, майбутній маршрут кімнати може містити `/person/I1`;
остаточні маршрути визначить ROD-009. Router передає вже декодований сегмент;
другого декодування, обрізання пробілів чи заміни регістру немає.
Початковий допоміжний метод підтримує поточні `@I…@`; інша форма XREF
потребує явного присвоєння канонічного ID в журналі.

`homePersonId` постійний і відокремлений від поточного центру та історії
перегляду. `initialGenerations` приймає цілі значення 1–11 і обмежує початковий
показ, а не набір даних. За рішенням власника від 22.09.2026 поточний сайт
використовує верхню межу `11`, яку карта обмежує фактичною глибиною родичів
для поточного центру; порожні зовнішні кільця не додаються. Для старих
конфігурацій без цього поля лишається `3`.
`PersonAppearance` містить `appearanceId`, `personId` та відносне покоління;
кілька появ із різними `appearanceId` ведуть до однієї людини й кімнати.
Проєкція, координати, поточний центр і камера не записуються до генерованого
родоводу або ручного `site.json`.

### Повторний експорт

[`identityManifestSchema`](../src/data/identity.ts) зберігає реєстр імпортів
із SHA-256 файла та записи `{ entity: { kind, id }, origins: [...] }`.
Кожне походження містить імпорт, GEDCOM XREF і, за потреби, шлях. Журнал
дозволяє простежити зміну ID без переписування всіх доказів і налаштувань.

1. Перший конвертер створює та зберігає журнал: канонічні ID людей із початкових XREF; іншим сутностям надає окремі ID, які далі не залежать від порядку, імені, дати чи тексту.
2. Для нового файла реєструється новий `importId` із його фактичним SHA-256. Навіть повторно використаний XREF не доводить тотожність людини.
3. До чинного запису явно додається походження нового експорту: `fixture-old/@I1@ → I1` та `fixture-new/@I42@ → I1`. Для вкладеного факту так само зіставляється точний шлях; `BIRT[0]` може стати `BIRT[1]`, але ID твердження залишається попереднім.
4. `resolveCanonicalId` повертає лише явно пов'язаний ID або помилку. Нові сутності отримують нові невикористані ID у журналі; ID вилучених записів не перевикористовуються. Старі походження залишаються для аудиту.
5. `site.json`, оцінки, матеріали й докази продовжують посилатися на канонічні ID. Вихідний XREF зберігається у новому `provenance`, URL та кімната залишаються `I1`.

Схема журналу відхиляє повторний імпорт/канонічну сутність, невідомий імпорт,
дві сутності одного типу на один locator та кілька сирих записів однієї
сутності в одному імпорті. Автоматичне злиття дублів цим контрактом не
передбачене. Перевірка SHA-256 проти фактичного файла та повноти журналу
виконується конвертером. Не можна генерувати ID з індексу при кожному запуску.

## Доповнення та порядок застосування

[`supplementsSchema`](../src/data/supplements.ts) не містить таблиці людей
або безумовних виправлень GEDCOM. Підготовка в ROD-005 має виконуватися так:

1. Розібрати GEDCOM, звірити імпорт та зіставити всі потрібні ID через журнал.
2. Створити сутності з джерельними значеннями; додати окремі матеріали, джерела, спогади й `additionalClaims` із поясненням, чому факт зберігається поза GEDCOM.
3. Застосувати `placeEnrichments` до явного `placeId`, зберігши `originalName` і додавши походження доповнення.
4. Застосувати `assessments` до конкретних `claim`/`relationship`; необов'язковий `reviewStatus` дозволено лише для зв'язку й він не підвищує достовірність автоматично. `primaryClaimIds` явно вибирають один варіант серед спільних цілі й поля. Вибір знімає попередній основний варіант у цій групі, але не видаляє альтернативу. Конфліктні вибори/оцінки — помилка, не «останній переміг».
5. Приєднати докази й налаштування, перевірити всі цілі та сформувати детермінований JSON. Походження кожної застосованої оцінки/вибору додається до сутності з ID запису доповнення (для `primaryClaimIds` — ID твердження).

Неприв'язане доповнення, невідомий ID, колізія чи непідтримана структура
мають потрапити у звіт. Не можна мовчки відкинути матеріал, записати його
іншій людині або згенерувати успішний результат із утраченим посиланням.
Виправлення основних персональних даних робиться у GEDCOM/RootsMagic з
наступним експортом, а не в `generated/family.json`.

## Межа перевірок і приклади

`familyDataSchema` перевіряє **структуру**, а не весь граф.
[ROD-006](Rodovid_Data_Validation_v1.md) додає
окремі предметні перевірки: унікальність ID усіх колекцій, існування всіх
цілей із таблиці вище, належність медіафрагмента джерелу, відповідність ролі
MIME (фото/PDF/аудіо), основний портрет серед фото людини, конфлікти основних
тверджень, повнота зіставлення доповнень та імпортів, календарна семантика,
повтори й цикли графа, суперечності D01–D06. Успішний `parse` сам по собі
не замінює цих перевірок. Схема журналу вже перевіряє його локальні колізії,
бо resolver не повинен повертати неоднозначний ID.

[`tests/fixtures/data-contract/`](../tests/fixtures/data-contract/README.md)
містить мінімальний, повний і некоректний JSON та приклад повторного
експорту. Файли медіа там умовні; вони перевіряють контракт, а не готовність
сімейного контенту до публікації. Тести в `src/data/*.test.ts` перевіряють
схеми, збереження точності дат/альтернатив, спільний документ, налаштування,
строгі помилки та стабільність ID. Посилання повного прикладу додатково
звіряються тестом; готовність реального набору перевіряється `npm run data:validate`.

Запуск: `npm test`, `npm run lint`, `npm run build` (включає TypeScript).
