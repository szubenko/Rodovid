## Мета

Узгодити єдину модель даних для перетворювача, карти, кімнат і доказів.

## Обсяг роботи

- Описати TypeScript/Zod-схеми людини, зв’язку, твердження, події, місця, джерела/документа, прив’язки доказу, спогаду та налаштувань.
- Задати домашню особу через @I1@; явно описати відображення GEDCOM ID в адресах на кшталт I1 і збереження походження записів.
- Визначити формат дат, основних і альтернативних тверджень, чотирьох рівнів достовірності та необов’язкових полів.
- Описати site/config, доповнення й явне зіставлення ID після повторного експорту; персональні дані залишаються у GEDCOM, generated JSON не редагується вручну.

## Критерії приймання

- [x] Усі сутності з §12.3 ТЗ мають схему та зрозумілі зв’язки між ID.
- [x] Один документ підтримує кілька прив’язок, одна людина — кілька екранних появ із спільним personId.
- [x] Збережені початковий текст дати, точність/невизначеність і невідомий життєвий статус.
- [x] Відсутня оцінка означає «Не оцінено»; QUAY не отримує автоматичного взаємно однозначного перетворення без окремого правила.
- [x] Приклади даних містять альтернативу, спільний документ і зміну ID; синтетичні приклади відокремлені від сімейного набору.

## Перевірка

Перевірити схеми на мінімальному, повному й некоректному прикладах; звірити модель з усіма сутностями ТЗ.

Блокерів для ROD-002 немає. Парсер та генерація сімейного JSON залишаються ROD-003/005; перевірка всіх посилань, конфліктів основних тверджень, календарної семантики та графа — ROD-006. У контракті явно відділено структурний `parse` від цих предметних перевірок. D01–D06 не виправлялися; сімейний журнал ID створюватиметься за фактичним результатом першого перетворення.
